Mi Libreta Financiera

Construí esta aplicación por fases pensando en personas que no son expertas en finanzas. Mi prioridad ha sido mantener claridad, privacidad y reglas de negocio que pueda validar.

El problema

Quería crear una herramienta financiera fácil de entender para personas que no quieren usar una hoja de cálculo ni conectar sus cuentas bancarias. Busqué que se sintiera como una libreta: registrar, separar, corregir y revisar sin esconder la lógica del dinero.

EnfoqueLocal-first y privacidad
ClienteReact + TypeScript
PersistenciaIndexedDB
Servicios mínimosD1 / Drizzle / Push

Qué construí

Dinero y reglas

  • Ingresos, gastos y transferencias con propósito obligatorio.
  • Apartados disponibles y reservados.
  • Validación de saldo antes de gastar o transferir.
  • Historial, correcciones y motivo de cambio.

Producto y experiencia

  • Pagos/tarjetas identificados por alias.
  • Objetivos, respaldos y tutorial guiado.
  • Evolución hacia múltiples libretas y comparación.
  • Pruebas con usuarios y cambios por feedback.

Arquitectura y decisiones

Cliente

React + TypeScript, PWA y almacenamiento local. Diseñé los registros financieros principales para que permanezcan en el dispositivo.

Servicios auxiliares

Uso Cloudflare D1 / Drizzle solo para funciones mínimas de beta, telemetría, feedback y recordatorios; no quiero convertir la nube en el libro contable principal.

Decisión clave: decidí separar los datos financieros sensibles de los servicios de beta y analítica.

🔒 Demo actual privada. El portafolio no enlaza la versión avanzada. Las muestras públicas provienen de una versión histórica temprana y sanitizada.

Evolución

  • Fase 1: edición, borrado, recálculo y saldos claros.
  • Fases 2–4: claridad visual, pagos/recordatorios y objetivos.
  • Fase 5: múltiples libretas y comparación.
  • Trabajo posterior: tutorial, configuración y funciones más complejas mantenidas privadas.

2 · Persistencia local transaccional

Centraliza cambios de estado, actualiza la marca temporal y cierra la base de datos incluso si algo falla.

async function mutateState(
  change: (state: LocalNotebook) => void
): Promise<LocalNotebookSnapshot> {
  const database = await openDatabase();
  try {
    const { state, transaction, store } =
      await readState(database, "readwrite");

    change(state);
    state.updatedAt = new Date().toISOString();
    store.put(state, STATE_KEY);
    await finishTransaction(transaction);

    return publicSnapshot(state);
  } finally {
    database.close();
  }
}

3 · Validaciones de negocio

Antes de modificar saldos se validan cantidad, propósito, existencia del apartado y saldo suficiente.

if (!state.setupCompleted || cents < 1)
  throw new Error("Escribe una cantidad mayor a cero.");

if (!purpose)
  throw new Error("Es obligatorio indicar para qué es el movimiento.");

const source = state.pockets.find(
  pocket => pocket.id === input.sourcePocketId
);

if ((input.kind === "gasto" || input.kind === "transferencia")
    && source.balanceCents < cents) {
  throw new Error("Ese apartado no tiene saldo suficiente.");
}

4 · Separación de telemetría y finanzas

La propia estructura documenta que la beta no debe guardar balances, notas financieras ni datos personales innecesarios.

// Beta diagnostics are intentionally separated from financial records.
// They use a random installation id and never store balances, amounts,
// notes, card aliases, photographs or email addresses.
export const betaInstallations = sqliteTable("beta_installations", {
  installId: text("install_id").primaryKey(),
  platform: text("platform").notNull().default("unknown"),
  appVersion: text("app_version").notNull().default("beta-1"),
  firstSeenAt: text("first_seen_at").notNull().default(sql`CURRENT_TIMESTAMP`),
  lastSeenAt: text("last_seen_at").notNull().default(sql`CURRENT_TIMESTAMP`),
});
